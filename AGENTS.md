# AI Agent Guide

This document helps any AI coding assistant - whichever model or tool it
is (Claude Code, Codex, Gemini CLI, Copilot, Cursor, Aider, a local
model, ...) - and any new human contributor work effectively with the
dopeIPTV codebase.  It is the single source of these instructions:
`CLAUDE.md`, `GEMINI.md` and `.github/copilot-instructions.md` only point
here.  Each module is kept small enough to fit in a 14-16B model's
context window.

**Start here:**

1. This file - what each module owns, the conventions, the quality gate.
2. [`docs/MAINTAINING.md`](docs/MAINTAINING.md) - branches, CI, how a
   release is cut, the website, keys and accounts, open work.
3. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) and
   [`docs/DEVELOPER_NOTES.md`](docs/DEVELOPER_NOTES.md) - how the parts
   fit together and why.

**Four rules above all others:** stability first - never break video
playback; Linux is the primary platform and a change for macOS or
Windows must not make Linux worse; one connection - assume the account
allows one connection to the provider (nearly every account does), so
nothing may open a second one by itself: a feature that needs one is off
until the person turns it on knowing what it costs, and asks first when
the limit is full or unknown; run the quality gate yourself before you
say something works.

**And a fifth, as binding: security and privacy.** dopeIPTV is to be
known for being open, private and very hard to attack. Every change and
every new feature follows [the security and privacy rules](#security-and-privacy-rules)
below; a change that cannot follow one stops and asks.

## Security and privacy rules

They hold for every change, however small, and for every new feature.
Each one names where it is already done right - copy that, do not invent
a new way. The threat model behind them (who could attack, what stops
them, what is honestly left) is [`docs/SECURITY.md`](docs/SECURITY.md).

1. **Nothing leaves without a reason the person can see.** Every outbound
   connection is something the person did (opened, sent, turned on), or
   an automatic one the transparency page lists (the update check). A new
   host or a new kind of data sent is added, in the same change, to the
   transparency page's hosts (`tools/transparency.py` `HOSTS`,
   `site/transparency/*.html` on the `website` branch), to the privacy
   policy if dopeiptv.org keeps anything of it, and to `docs/FEATURES.md`.
2. **dopeiptv.org's services** go through `build_check.secure` (https to
   dopeiptv.org itself), `allow_redirects=False`, never from a modified
   build (`build_check.allowed`), and carry nothing that says who asks: no
   account, name, supporter key, title or address. A value the server
   could use to tell people apart is a hash or a code from the person's
   own secret (`report.py`'s answer codes, `sync.auth_of`), never an id
   the app makes up and keeps. What the server keeps, and how long, its
   docstring and the privacy policy say - and only that is kept.
3. **Third parties** (TMDB, Trakt, Simkl, OpenSubtitles, radio-browser,
   Plex.tv, GitHub...): https with certificate checks (never
   `verify=False`; `core/cert_pin.py` reading a certificate before pinning
   it is the one exception), the least the service needs, and nothing
   about a private playback unless the person asks for it right then.
4. **Private viewing.** Anything that keeps or sends what plays asks
   `privacy.playback_private(kind, key)` (or `private_key`) for that very
   playback - never the switch alone - and keeps and sends nothing. A
   title, channel, programme or address in a log goes through
   `privacy.for_log`.
5. **Everything from outside is hostile**: providers, guides, boxes and
   servers on the network, files, subtitles, images, web services, the
   phone remote's and server mode's clients, a backup being restored. It
   is size-limited while it is read (`epg.read_capped`), parsed with the
   safe helpers (no XML entities or DTDs - `epg.refuse_entities` -,
   bounded nesting, no regex that can run away), numbers range-checked,
   never shown as markup (`Qt.TextFormat.PlainText`, `ui/widgets.plain_text`;
   a QMessageBox's or QInputDialog's words through `plain_text`:
   `tests/test_security_rules.py`'s `OWN_WORDS`),
   never an address the app then fetches unless it is one the app should
   (no `file:`, no internal address an outsider chose), never a path
   outside the folder it belongs in, and never unpickled: no pickle in the
   app (`tests/test_security_rules.py`). A source on the internet's stream,
   picture and guide addresses never name this computer or a link-local
   host (`core/stream_address.py`; AceStream's engine on port 6878 the one
   exception), and the app's own requests never land there nor follow a
   redirect inward, whatever a name resolves to (`core/dest_guard.py`: a
   new way to make requests goes through `core/_lazy_requests.py`'s
   session or `core/net_adapter.py`, never around them).
6. **Secrets** - logins, tokens, the sync and room codes, keys - stay in
   the settings files (0600 in a 0700 folder, `core/settings_files.py`).
   Never in a log (`core/log.py`'s filter is the net, not the plan: do not
   log them), a report (`core/report.py` scrubs, with the person's own
   values), a URL that is logged, a crash file, a cache, or a backup the
   person did not choose to keep them in. Tokens are compared with
   `hmac.compare_digest`; anything random that guards something comes from
   `secrets`.
7. **Servers on this computer or the network** bind only where they must
   (loopback unless the feature is for the network), take a token of 128
   bits or more on every request (the HDHomeRun protocol's few endpoints,
   for this computer's own networks only, are the exception - see
   `home_server.local`), check the Host header against DNS rebinding and
   the Origin / Sec-Fetch-Site so a web page cannot use them, limit sizes,
   headers and time, never serve a file outside their folder, and give
   their pages a CSP of their own hashes (`core/phone_page.py`).
8. **Programs the app starts** get an argument list, never a shell; text
   from outside goes where it cannot be read as an option; ffmpeg reads
   only the protocols the job needs; the command after a recording runs as
   the person wrote it, never with outside text spliced into its words
   (`core/rec_extras.py`).
9. **Cryptography** only from what is here - `core/chacha20poly1305.py`,
   `core/ed25519.py`, HKDF in `core/sync.py`, `hashlib`, `hmac`,
   `secrets` - used the way it is already used. A new scheme needs a
   written design, test vectors and a line on the transparency page.
10. **Updates and builds**: only what the signed checksum list names is
    installed (`selfupdate.signed_asset`), and nothing the app downloads to
    run is trusted by a list downloaded beside it (`core/ytdlp_pin.py`: the
    build checks the signature); the update key signs only in its own step,
    the build jobs have the build key alone; downloads follow redirects only
    over https (`selfupdate._get_https`); a new dependency needs a reason
    in its commit and a pinned version; workflows keep least privilege and
    pinned actions.
11. **Transparency**: a change to anything the transparency page shows
    updates the page's words and its code excerpts (`tools/transparency.py`)
    in the same round, and the page never claims more than the code does.
    Honest limits are written down, not left out.
12. **Tests**: every rule a change touches has a test that fails when the
    rule is broken; `tests/test_security_rules.py` holds the ones that read
    the whole code base, and a new exception there needs its reason beside
    it.
13. **Before a release**: make the review kit (`tools/review_kit.py --app
    <checkout> --ref testing` on the `website` branch), give its `ALL.txt`
    to at least one independent AI assistant, fix or answer every finding,
    and record the round in `docs/SECURITY_REVIEWS.md`.

When making changes:

- **UI changes**: find the method by name across `ui/main_window.py` and
  the `mw_*` mixins (e.g. `open_settings` lives in `mw_settings.py`; the
  window's widgets are made in `mw_build.py` and `mw_build_detail.py`).
  A mixin method resolves on `MainWindow` via MRO, so a pure move between
  them never changes behaviour.
- **Playback**: `media/embedded.py` for the in-app player (its DVR row
  and timeshift timeline in `media/rewind_bar.py`; its tracks, overlays,
  pop-out mirror, sound effects, sleep timer and stats in the mixins
  beside it - each has its row above), `media/players.py` for external
  players.
- **Theme/style**: `ui/theme.py` contains `THEMES`, `ACCENTS`, palette
  dict `P`, and `build_style()`.
- **Data/API**: `providers/client.py` for HTTP calls, `core/stores.py`
  for persistence, `providers/epg.py` for programme data.
- **Recording**: `core/recording.py` is self-contained; the
  `mw_recording` mixin calls its public API.

## Conventions

- Python 3.11+, `from __future__ import annotations` in every file
- PyQt6 (not PyQt5) - all Qt imports use the PyQt6 namespace
- No comments unless the "why" is non-obvious
- Type hints on public method signatures
- UI strings, comments, docstrings, and commits in English
- `P` dict from `ui/theme.py` for all colors (never hardcode hex)
- `ACCENT` string from `ui/theme.py` for the user's chosen accent color

## Common tasks

**Add a new dialog**: create a class in `ui/dialogs.py` - or, for a
feature with windows of its own, in a module beside it as
`ui/feedback_dialogs.py` and `ui/backup_dialogs.py` are - import it where
it is used, wire it to a menu action.

**Add a new setting**: add the QSettings key read/write in the builder of
the page it belongs to - `build_<page>(ctx)` in its group's module
(`ui/set_watch.py`, `ui/set_content.py`, `ui/set_services.py`,
`ui/set_system.py`; Nerd's in `ui/nerd_settings.py`): a `card.row()` or
`card.toggle()`, run the first time the page is shown or searched - never
as the window opens - and the write-back in that page's
`commit_<page>(put, changed, final)` beside it. What the builders share
(`own()`, `nerd_link()`, `soon`...) is `SettingsContext` in
`ui/mw_settings.py`. Rows are found by the Settings search automatically.
Never show a widget before it is in a row (`setVisible(True)` on one with
no parent is a window of its own: on GNOME the pointer spins for seconds);
`tests/test_settings_lazy.py` fails on one. A number takes a `Stepper` (not a bare `QSpinBox`), a
time offset a `DurationSpin` and a size a `SizeSpin`, each in a `Stepper`;
a set of on/off choices of one kind takes `Chip`s in a `ChipGroups` rather
than a column of switches. Settings apply as they change (`commit()` in
`open_settings`, debounced, plus once on Close): write the new key there
with `put()`, which stores only what changed. A section is a borderless
surface with hairlines between rows, and controls are filled, not
outlined - don't add borders back, and don't drop the surface either: with
neither, the rows ran together.

**Where a setting goes - decide it before you write it.** Settings are
grouped by what a person is doing: WATCH (Playback, Picture and sound,
Guide, Multiview, Recording, Casting), CONTENT (Sources, Mine, Local
files, Posters and info), SERVICES (watch history -
Trakt, Simkl -, Sync, Integrations), SYSTEM (General, Appearance, Keyboard
shortcuts, Profiles, Parental lock, Advanced) and NERD (Status, Network, Boxes and lists, Player, Remote
and automation, Diagnostics). Every row there is today, page by page and
section by section with the key it stores, is in
[`docs/SETTINGS_MAP.md`](docs/SETTINGS_MAP.md) - look there first, and add
the new row to it (`tests/test_settings_map.py` checks every page is in one
group, every row on one page, and that the map names every page).

- Put it where someone would look for it, not where the code that reads
  it lives.
- One setting, one place: another page that needs it links to it, never a
  second copy.
- A feature with a few settings gets a section on the page it belongs to,
  not a page of its own; a new page only for a service of its own.
- A source's own option goes in that source's page (`ui/source_page.py`,
  on the tab it belongs to, with an `Origin` mark), marked as its own,
  with the shared one shown as shared.
- A profile's own setting (`core/profiles.py` declares which) stays on the
  page it belongs to, marked "This profile's" (`own()` in `open_settings`,
  shown with two profiles or more); a new one is added to the declared
  split, or it is the household's.
- A Nerd-only option goes under NERD, and the everyday page it belongs
  beside gets one link row to it ("4 Nerd settings for ... -> Nerd >
  Player"): `nerd_link()` in `open_settings`, shown only while Nerd is on.
- If no page fits, stop and ask rather than add a page or a stray row.

**Add a theme**: a palette in `THEMES` (`ui/theme.py`) with every key the
others have, `"light": True` for a light one and `"accent"` for its own
accent colour, plus `theme_<key>` in `i18n.py` and every `locale/*.json`.
`tests/test_theme.py` checks the keys and that the text stays readable.

**Add a new data store**: add a class to `core/stores.py` following the
pattern of `FavoriteStore` or `HistoryStore`.

**Change the channel list appearance**: modify `ChannelDelegate` paint
methods in `ui/channel_list.py`.

- **Before deleting, moving or renaming a file under `packaging/`, `docs/`
  or any other committed asset, grep for it INCLUDING hidden directories.**
  Plain `grep -r` and ripgrep both skip `.github/`, so a reference from a
  workflow step is invisible to the obvious check - which is exactly how
  `packaging/io.github.slimture.dopeIPTV.png` was removed while the
  Windows job still built its `.ico` from it, and the release build went
  red. Use `grep -r --include=... . .github` explicitly, or `rg --hidden`.
  `tests/test_packaging_icons.py` now fails on any repo path a workflow
  names that does not exist, so this cannot reach CI again - but the habit
  is cheaper than the test.
- **Branches: app work goes on `testing`, releases go `testing` → `main`,
  the website lives on `website`. No other branches, not even for a CI
  experiment.** A scratch branch pushed to GitHub runs workflows, leaves
  commits and artifacts behind, and confuses the history - and it happened,
  while probing a Windows runner for issue #19. To exercise the Windows
  release job without tagging, run `release.yml` by hand (`workflow_dispatch`)
  on `testing`; the "Attach to release" steps only fire on a tag.
- **A test may only import what CI installs**, which is `requirements.txt`
  plus ruff, mypy and pytest - see `.github/workflows/ci.yml`. A green run
  locally proves nothing about a module that happens to be on this machine
  and not on the runner: PyYAML was imported by one test, passed here, and
  failed CI with `ModuleNotFoundError`. Prefer reading a file as text over
  adding a dependency to the whole suite for one assertion.
